# War Room — Build log

How this was built with an AI coding agent (Claude Code), phase by phase: what was asked, what was done, and where the agent or I corrected course.

## Phase 1 — Setup, types, data loading (2026-11-18)

**What I asked for**
- A Next.js (App Router) + TypeScript + Tailwind project, `.gitignore` first, all types in one file, `data/snapshot.json` loaded, and a realistic mock snapshot if I hadn't run `fetch_league.py` yet.
- Before any code: show me the types file and folder structure.

**What happened**
1. **Plan before code.** The agent read `fetch_league.py` and `recommend_prompt.md` first, then proposed the folder structure and the full `lib/ontology.ts`. I approved it before anything was written.
   - It proposed **two layers**: raw wire shapes (snake_case, exactly what the Python script and the prompt's JSON format produce) and ontology objects the UI uses. `lib/snapshot.ts` is the only code that translates between them.
   - It **derived `ProTeam`** rather than duplicating each schedule on every player: the snapshot stores games per player, and the loader groups them by team.
   - It **pushed back on three separate routes** and proposed one page with tabs: a single Claude call returns lineup, pickups and briefing together, so one fetch should feed all three screens.
   - It flagged decisions for me instead of guessing: Override is stored as `dismissed` (no third state), `ADD_DROP` with an underscore instead of `ADD-DROP`, and recommendation ids include the snapshot timestamp so approvals don't carry over to a new snapshot.
2. **`.gitignore` first.** Covers `.env*`, cookie files, `node_modules`, `.next`, `.vercel`, and Python caches. Then `git init`.
3. **Scaffold.** `create-next-app` installed Next 16.4 + React 19.3 + Tailwind 4.3.
4. **Mock data.** `scripts/make_mock.py` writes `data/snapshot.json` (13 roster players + 40 free agents, H2H categories, 9 teams) in the exact shape `fetch_league.py` produces. It also writes a `data/previous.json` one day earlier, so the briefing has something to compare in phase 3. The mock tells a story on purpose: one player OUT on IR, one day-to-day starter, a cold rostered guard, and several free agents with 4 games and rising form.
5. **Loader + header.** `lib/snapshot.ts` normalizes the snapshot into a `WorldState`. The header shows league, record, week, POINTS/CATEGORIES, the snapshot time, and a red MOCK DATA label while the data is fake. A plain roster table on `/` proves the pipeline end to end.
6. **Checked.** `tsc`, `eslint` and `next build` pass. The page renders in the browser with 13 roster players, 40 FAs and 27 pro teams.

**Corrections and course changes**
- *Agent, self-corrected:* `create-next-app` won't scaffold into a folder that already has files, so the agent scaffolded in a scratch folder and copied only the config over. It skipped the template's boilerplate README and SVGs.
- *Agent, self-corrected:* the template ships Next 16 with `cacheComponents` on, and a note warning that APIs differ from the agent's training data. Instead of assuming, the agent read the bundled Next docs. They confirm that `readFileSync` is treated as predictable and prerendered, so the snapshot is baked in at build time. That fits "commit the snapshot, redeploy."
- *Agent, self-corrected:* the first `tsc` run failed on `LayoutProps`. That global type is generated by `next build`, and the error cleared after the build.
- *Agent, small deviation from the approved types:* it added an optional `_mock` flag on `RawSnapshot` and `isMock` on `League`, so mock data is visibly labeled and can't pass for real data in a demo.
- *Agent, timezone catch:* `fetch_league.py` writes local time with no zone. The agent formats it as written, so Vercel's UTC servers don't shift the displayed snapshot time.

**Open for later phases**
- `fetch_league.py` overwrites `snapshot.json` and never writes `previous.json`. The "what changed" briefing needs the old snapshot rotated to `previous.json` before each pull. This is a small change to the script, still to be decided.

## Phase 2 — Three screens on mock recommendations (2026-11-18)

**What I asked for**
- **Today:** every lineup player with a START / SIT / MONITOR tag, a one-line reason, 2–3 factor chips, confidence, and Approve / Override.
- **Pickups:** up to 3 add/drop cards, comparing the two players side by side.
- **Briefing:** up to 4 lines.
- Calm and dense, like an operations console. One accent color. The reasoning chips are the main design element.

**What happened**
1. **Mock suggestions in the real wire format.** `lib/mock-recommendations.ts` is hand-written JSON in exactly the shape `recommend_prompt.md` asks Claude for: 13 lineup calls, 2 pickups, 4 briefing lines. Every number in it was read out of the mock snapshot, not invented. Phase 3 swaps the source without touching the screens.
2. **A validating run builder.** `lib/recommendations.ts` turns wire JSON into `Recommendation` objects linked to the `WorldState`. It drops anything that doesn't link to a real object: an unknown player id, a "drop" who isn't on my roster, an "add" who isn't a free agent. It also caps chips at 3, pickups at 3 and briefing lines at 4. This exists now so phase 3's live model output goes through the same check.
3. **Approvals.** `lib/approvals.ts` is a small `useSyncExternalStore` hook over localStorage.
   - It survives reloads, and other open tabs stay in sync.
   - It falls back to memory if storage is blocked.
   - It keeps only the current snapshot's decisions.
   - Undo returns a card to pending.
4. **The chip.** Label, value and a direction glyph (▲ ▼ –) on a faint green, red or neutral tint.
   - Direction means "for or against this player's outlook," not "the number went up," so a falling turnover count reads green. The shape carries the meaning and the color only reinforces it. Screen readers hear "supports" or "works against."
   - A value like "21.1 vs 19.5" shows the baseline quieter than the headline number.
5. **Screens.**
   - **Today** groups the roster into Starters / Bench / IR in ESPN slot order. Each row has the slot, the action tag, the name with team, position and game count (plus an injury flag), the reason, the chips, a 3-bar confidence meter, and the controls.
   - **Pickups** puts the chips on top, then an add-vs-drop table over the last 15 days: games plus the 9 categories (or fantasy points in a points league), with the better value in bold and turnovers counted lower-is-better.
   - **Briefing** is a numbered list that says which earlier snapshot it compares against.
   - The tabs show pending counts. A footer line says approving only records a decision and moves are made in ESPN.
6. **Checked in the browser.** Approve and Override persist across a reload, and the counts update. All three tabs render. At 375px wide the layout stacks with no horizontal page scroll; the pickup table scrolls inside its card. `tsc`, `eslint` and `next build` pass.

**Corrections and course changes**
- *Agent, caught before running:* the first draft of the run builder stamped `new Date()`. The Next 16 docs it read in phase 1 say timestamps inside a prerendered component need special handling, so the timestamp is now passed in. This was fixed before it ever failed.
- *Agent, self-caught in the browser:* the new chip tints rendered as plain black borders. The running dev server hadn't picked up new `@theme` tokens, and restarting it fixed this. The agent checked computed styles in the page rather than trusting the code.
- *Agent, design self-critique after the first screenshot:*
  - 13 solid black Approve buttons made a loud column down the page, so Approve became outlined and Override became a quiet text button.
  - Dimming a whole overridden row also dimmed its Undo link, so now only the content dims.
  - The pickup table's last column had no right padding.
  - On phones the header broke "MOCK DATA" across two lines.
- *Agent, scope call:* it showed 2 pickups instead of 3. The only third candidate in the mock data would have dropped Jalen Suggs, the player the lineup tab tells you to start. Contradictory advice across tabs would undercut trust.

**Open for phase 3**
- The prompt doesn't say what "direction" means on a factor. The UI treats it as for/against the player, so the system prompt should state that explicitly, or Claude may mark a falling turnover count as "down."
